# agent-* pipeline set for OpenCode v2

This repo: 6 pipeline agents = 6 roles × 1 variant (the plain set; the `-bmad` overlay was removed 2026-10-18), plus the standalone agents (`planner`, `code`, `ask`, `debug`, `review`) and the `0-pipeline` → `7b-docs-dev` SDLC stage agents, 2 `/pipeline*` commands, and the plan templates. All of them are generated by rulesync from `.rulesync/` sources.

Roles: `coord` (primary), `plan`, `research` (on demand), `test`, `dev`, `review`, `fuser` (on demand, user-launched — fuses parallel runs of a ticket).
Variants: only the plain (base) set ships in this repo. The mechanism for overlays remains: overlay names lead with the overlay marker (`agent-dev-bmad`, not `agent-dev-<domain>-bmad`) so no plain name is a prefix of its overlay's agent names — exact matching is verified on v2.0.24 (see known-issues #1), and prefix-free names stay safe under any prefix-like behavior (wildcard rules, saved approvals, UI grouping). An overlay coordinator launches only its overlay's subagents. `/pipeline` + `/pipeline-resume` target the plain variant.

## Install / regenerate

`rulesync generate` produces all tool surfaces from `.rulesync/` (targets/features per `rulesync.jsonc`); edit the sources there — role prompts, permission blocks, commands, rules — rather than the generated files, then regenerate. Commit sources **and** generated surfaces together. `generate --delete` sweeps orphans (renamed/removed agents); run generate twice to confirm the second run is a no-op.

## Domain context

Agent files do **not** duplicate repo context — MCP servers, layout, git rules, plans, and verify commands live only in `AGENTS.md` (generated from `.rulesync/rules/`, auto-loaded into every session). The pipeline's contract blocks (plan folders, read order, RESULT schema, kickoff, model routing, gates) and each role's process/hard-rules live in the hidden `pipeline-*` skills (`pipeline-conventions`, `pipeline-role-<role>`, `pipeline-kickoff`, `pipeline-models`, `pipeline-gates`); the agent files are thin frontmatter + `/skill` call skeletons that compose them. The remaining accepted duplication is the **skills lists**: every agent file carries its own `## Skills` section (plan-driven loading first, then any role-pinned MUST-load list, then dynamic picks). To change repo context, edit `.rulesync/rules/` and regenerate; to change the contract or a role, edit `.rulesync/skills/pipeline-*/`; to change which skills an agent loads, edit the agent source and regenerate.

## How the pipeline runs

1. `/pipeline <request>` → `agent-coord` runs the kickoff (ask slug, ONE multi-select model question — Qwen Large / Qwen 27b / Qwen Flash / Local-gpu-ai — and run tag; then name worktree/branch/session via the `opencode` tool, capturing its own sessionID for `coord_session`), does the 3-skill intake on the request, and resolves (or creates via `agent-plan`) the feature folder `.agents/plans/<yyyy>/<yyyy-mm>-<type>-<slug>/` (blanks from `.agents/plans/templates/`). If `plan_status != "approved"`, Phase 1: `agent-plan` plans into the folder and presents the plan to the user; coord continues only once `STATE.json` shows `approved` — never approves on the user's behalf. `/pipeline-resume` picks up the active ticket (skips the kickoff).
2. **Tests phase**: coord launches `agent-test` ONCE for the whole plan — it writes the tests for every chunk (each chunk file lists them under "## Tests") in a single session, before any implementation; its sessionID is recorded as `test_session` in `STATE.json`.
3. Per chunk, in wave order, one at a time: dev (implement; tests are read-only to it) → review (runs the validation commands/full suite first, then reviews) → (fix routed back to the chunk's dev session, fresh if gone → fresh review — reviews are never continued, max 3 rounds). If review judges a test itself at fault it returns BLOCKED with `validation_at_fault` — the reviewer edits nothing; coord routes the fix silently to the test session (`test_session`; fresh `agent-test` session if gone), which returns NEEDS_INFO when a repair would change functionality — only that escalation reaches the user. When all chunks are done, coord runs a final review of the whole plan (full diff against every acceptance criterion, plus the full suite) before marking it complete. Research needs bubble up to coord at any point (RESULT `open_questions`, planner flag); coord launches `research`, which writes `RESEARCH.md` into the feature folder for every later agent.
4. Every subagent returns a `RESULT` block; the coordinator copies it into the ticket's `STATE.json` before doing anything else, and appends reported `friction:` items (plus its own) to the ticket's `FRICTION.md` with the resolutions used — every agent reads that file at run start, so known workarounds are not rediscovered. The user triages entries later (`open` → `fixed`/`ignored`); entries are never deleted. Whenever a coord session ends with `open` friction items, it asks ONE multi-select question ("Should any of this friction be addressed?") and launches a fresh `agent-plan` per checked item, each planning its fix as a new ticket.
5. A chunk is `done` only with dev DONE + review APPROVED, with the validation commands shown passing in review's `commands_run`. The final whole-plan review runs on the planning-tier model.
6. **Fusion (optional, user-launched):** when several runs of the same ticket exist (one branch/worktree each), `agent-fuser` compares them — planning quality across runs, branch code diffs (unique features, what to port/drop), research deltas, friction deltas — and reports. The user confirms the base branch and, per genuine conflict, which branch to source from (every such answer gets a mandatory follow-up confirmation). The fuser then `session_move`s into the base worktree and writes `FUSION-REPORT.md` + `<plan-file>-fusion.md` (the base plan file's name + `-fusion.md`, the one sanctioned second plan file in a ticket folder), gets the plan confirmed, and hands it back to the base branch's session — a prompt to `coord_session` (from the ticket's `STATE.json`, via the OpenCode session API) telling it to replan the ticket around the fusion plan; `done` chunks stay done.

Chunking rules live in the plan prompts: S tasks grouped up to 5, M tasks up to 2, L alone, every chunk mergeable on its own, `depends_on` → topological `wave` order. Plans record verification commands under "Commands" — this repo has no unit-test suite, so those are the validation commands from `AGENTS.md` (`helm lint`, `helm template`, trio/custom-values grep checks).

## Permissions summary (v2 ordered rules, last match wins)

| agent | edit | subagent | shell | MCP |
|---|---|---|---|---|
| coord | `.agents/plans/**/{STATE.json,DECISIONS.md,FRICTION.md}` only (starts from deny-all) | plan/research/test/dev/review of same variant | none (deny `*`) | none (deny `*`) |
| plan | `.agents/plans/**` only | none | git reads allowed, else ask | `admin*` deny; `readonly*`/`global*` allow |
| research | `.agents/plans/**` only (writes `RESEARCH.md` at the exact feature-folder path from its launch message) | none | git reads allowed, else ask | as plan; plus `webfetch`/`websearch` |
| test | test paths (`charts/**/tests/**`, `containers/**/tests/**`, top-level `tests/**`) + context allows only (starts from `edit * deny`) | none | git reads + `helm lint/template/unittest` allowed, else ask | as plan |
| dev | everything except the test paths (`charts/**/tests/**`, `containers/**/tests/**`, `tests/**`), plans; context files per-table (see `references/permissions.md`) | none | git reads + `helm lint/template` allowed, else ask | as plan |
| review | `.agents/plans/**` only (never edits code or tests; a faulty test escalates via coord to the test session, user-confirmed) | none | git reads + `helm lint/template` allowed, else ask | as plan |
| fuser | `.agents/plans/**` only — the confirmed base worktree's ticket folder, entered via `session_move` (writes `FUSION-REPORT.md` + `<plan-file>-fusion.md`) | none | git reads (`status/log/diff/show/branch/merge-base/worktree list`) + `helm lint/template` + `opencode api` session get/prompt allowed, else ask | as plan |

Every role can ask the user questions with the `question` tool — questions only reach the user when explicitly asked, so all prompts say to use the tool when blocked on a decision only the user can make (pipeline subagents prefer `open_questions` in the RESULT block first). Skills are unrestricted everywhere, except coord: it denies the other roles' `pipeline-role-*` contract skills (it coordinates — it must not absorb their contracts).

MCP tools are permissioned as action `<server>_<tool>`; unsupported characters become `_`, so the prefix rules `readonly*` / `admin*` / `global*` match both `readonly-foo` and `readonly_foo` spellings.

## Things to verify on your build (known v2 issues as of 2026-10)

1. Frontmatter `permissions:` was silently ignored on 2.0.12–2.0.14 and, on later builds, whenever an unknown key is present. **Verified loaded and enforced on v2.0.24 (2026-10-14, live probes)**: a coordinator attempting cross-variant launches got `Permission denied: subagent` for the other variant's agents while its own four succeeded; its `subagent` tool schema listed exactly its 4 same-variant agents (the list is permission-filtered). Matching is whole-value (exact for patterns without `*`). These files use only `description`, `mode`, `color`, `permissions`. Check with:
   `opencode api get /api/agent/agent-dev` → rules must appear in top-level `permissions`, not `request.body.permissions` (against the server that owns the repo location — pass `x-opencode-directory: <repo>` when querying a shared/background service; `opencode api --standalone` may answer before agents load and return an empty list).
   If not applied, move each block to `agents.<id>.permissions` in the OpenCode config.
2. Do a live test: `opencode run --agent agent-review "write hello.txt"` must be denied.
3. Shell is `ask` for dev/review outside the allowlist (git read commands and `helm lint/template`). For unattended runs, add your exact commands as `allow` rules in the agent sources; keep the allowlist narrow.
4. Commands live in `.opencode/commands/` (generated): `/pipeline`, `/pipeline-resume`. They route to `agent-coord`, and the `!`…`` line discovers the tickets' STATE.json files and injects them at kickoff.
5. In OpenChamber, never start a message with `/skillname` (404 bug); mention skills mid-message or let the agent call the `skill` tool. (This is why the agent prompts say never to START a message with `/skill-name` even though skills are force-loaded via `/` in their lists.)
6. All `agent-*` agents are user-selectable: `mode: all` (coord is `mode: primary`), so any of them can be driven directly from the agent picker, not just launched by coord.
